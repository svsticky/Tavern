# Migrations

_Official docs by Microsoft can be found [here][docs]_

We manage the database with migrations.
A more detailed explanation will be given later, but for now:

## What are they

Long story short, the database does not fall under git, but we must have a way to allow every machine which ever
clones this repository to update the database to (any but most commonly) the latest version.
In other words, if we can define 'changes' to the database step by step such that every machine can follow those steps
to the latest vesion of the database, we have a way of version control over the database: we control those steps.
Those steps are migrations: they state explicitly how to alter you database to reach a specific version.
You can't just checkout (git checkout) a database version though: adding a column to a table your database currently
does not have is not possible, and 'just' creating that table if it is missing is also not trivial.
That's the intuition behind migrations: at any point in time, if you made changes to the database design, you generate
a migration from the last migration to your current design - creating an extra step. If this step/migration is traversed
by another machine, it can update it's db to match your design. This works backwards too, if done properly!

All migrations live under the `Migrations` folder.
They're quite voodoo magic, but Entity Framework knows how to interpret them.

## How to apply migrations (update db)

You must use the Entity Framework tool in a CLI (`dotnet ef`), or your editor if it is GOATed.
If not run from the devcontainer, make sure you install the right version and such (mimic `.devcontainer/Dockerfile`).

Now that everything is installed, just update your database:

```bash
dotnet ef database update                    # When local folder is a C# project
dotnet ef database update --project Backend/ # When the local folder `Backend` contains the project to migrate
```

## How to create migration (make design changes permanetn)

Migration definitions only look at your code - when creating changes it never bases them on your current database definition.
Frankly, EF Core never looks at your database untill you apply migrations (as far as I understand it currently).

So, how to create a new migration:

```bash
# When local folder is a C# project:
dotnet ef migrations add ADescriptiveNameToMakeLifeAndLoggingEasier
# When the local folder `Backend` contains the project to migrate:
dotnet ef migrations add ADescriptiveNameToMakeLifeAndLoggingEasier --Project Backend/
```

Note the name of your migration - help others understand the history of the migrations!
The migration was generated by looking at the current 'snapshot' of the database (a file last generated by EF Core),
and comparing it to the project.

[docs]: https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/?tabs=dotnet-core-cli

Don't forget to test your migration by applying it to your database!
**More importantly, commit changes to the `Migrations` folder or the rest won't be able to bring their database in the
right state!**
Less importantly, also make sure you can traverse this migration backwards: to be able to undo it.
Going back in time is important in git, and so it is in the world of migrations.
